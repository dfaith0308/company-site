## 2026-09-28 / 첫 점검 때 사이트 자체는 고치지 않음
- 상황: "확인하고 수정할 부분을 찾아 보고하라"는 지시. 바로 고칠 수 있는 것(글씨 색, 쉼표 등)도 있었다.
- 결정: 이번에는 점검·기록만 하고 사이트 화면(index.html 등)은 건드리지 않았다.
- 이유: `main`에 올리면 곧바로 실제 사이트에 반영되는 구조이고, 배포는 사용자가 지시할 때만 한다는 규칙이 있다. 또 문제 대부분이 대표 결정(이미지, 카톡 채널, 회사명, 판매 조건)이 필요하다.

## 2026-09-28 / 랜딩페이지 관리자(글·사진 편집 화면) 필요 — 대표 요청
- 상황: 이 페이지는 광고용이다. 대표가 개발자 없이 문구·사진을 블로그 글 쓰듯 바꿀 수 있어야 하고, 광고 효과를 숫자로 볼 수 있어야 한다. 지금은 글자 하나 바꾸려 해도 코드를 고쳐야 하고, 방문 통계도 없다.
- 결정: 필요하다는 데 동의. 단, 설계서에 없는 새 기능이라 표준 3절에 따라 바로 만들지 않고 설계서 초안 → 대표 확인 → 제작 순서로 간다.
- 이유: 방식(직접 만들기 vs 외부 도구)에 따라 비용·기간이 크게 달라서 대표가 정해야 한다.
- 재검토 시점: 대표가 방식과 범위를 정했을 때

## 2026-09-28 / 랜딩 관리자 방식·범위 확정 (대표 결정)
- 상황: 직접 만들기 vs 외부 도구, 가벼운 버전 vs 무거운 버전.
- 결정: 직접 만든다. 무거운 버전(칸 추가·순서 변경, 광고별 페이지, A/B 비교). 광고 매체는 네이버·인스타·유튜브.
- 이유: 식식이뿐 아니라 D.FAITH 다른 서비스에도 재사용 가능 (대표).
- 재검토 시점: step1 완료 후

## 2026-09-28 / 관리자를 별도 새 프로젝트로 만듦 (Claude Code 판단)

- 이유: 다른 서비스에도 쓸 도구라 식식이 콘솔에 묶이면 안 된다. 만드는 방식은 기존 서비스와 동일(Next.js + Supabase)로 해서 관리 부담을 줄인다.

## 2026-09-28 / 편집 방식은 "칸 쌓기" (Claude Code 판단)
